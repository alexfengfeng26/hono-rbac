# 陪玩系统快速落地方案（多行业通用版）

> 版本：v2.0（2026-08-19 整改：从「从零选型」改为「基于本仓库现有 RBAC 骨架演进」）
> 依据：`游戏陪玩系统管理后台功能方案_v1.1.md`、`陪玩系统手机端功能与字段说明.md`、`功能清单.xls`、本仓库代码（`app/lib/rbac/`、`app/lib/db/schema.ts`）
> 定位：把「游戏陪玩」抽象为通用的**「陪伴/陪练服务撮合平台」**，一套系统、多行业复用；IAM 与后台框架已就绪，只做领域层。

## 一、方案定位与目标

### 1.1 一句话定位

> 一套 **「服务提供者 — 平台 — 消费者」双边撮合系统**：服务方发布服务 → 认证准入 → 消费者下单支付 → 服务交付 → 平台/服务方分账结算。游戏陪玩只是它第一个落地场景。

### 1.2 核心目标

| 目标 | 量化指标 |
| --- | --- |
| 快速落地 | 领域层 MVP **2-3 周**上线（IAM/后台骨架已完成，见第二章） |
| 多行业复用 | 行业切换 = **改配置不改代码**，新行业接入 ≤ 1 天 |
| 低成本启动 | 本仓库单进程架构（HonoX + SQLite），1-2 人即可运营 |

### 1.3 适用行业（源生 + 可迁移）

| 行业 | 服务方 | 消费者 | 典型服务 |
| --- | --- | --- | --- |
| 游戏陪玩（源生） | 陪玩/代练 | 老板 | 上分带飞、娱乐陪玩、护航代练 |
| 健身陪练 | 健身教练 | 学员 | 私教课、减脂带练、动作纠正 |
| 才艺陪练 | 声乐/舞蹈老师 | 学员 | 练琴陪练、舞蹈陪练、K歌陪唱 |
| 陪诊 | 陪诊师 | 患者/家属 | 挂号陪诊、取药代跑、检查陪同 |
| 家教陪学 | 老师/学霸 | 家长/学生 | 作业辅导、考前冲刺、陪读 |
| 宠物陪玩 | 宠托/遛狗师 | 宠主 | 遛狗、上门喂养、宠物陪伴 |

## 二、现有基础（本仓库已具备，无需重建）

当前仓库是一个**已跑通的 RBAC 管理后台骨架**（HonoX + better-sqlite3 + drizzle-orm + Tailwind 4/daisyUI + Vitest），以下能力直接复用：

| 能力 | 实现位置 | 陪玩系统的用法 |
| --- | --- | --- |
| 用户 + 会话 | `users` / `sessions` 表，`app/lib/auth/session.ts`（cookie 会话，7 天 TTL，停用账号自动拒登） | 扩展为用户/服务方/管理员统一账户体系 |
| 角色-权限 RBAC | `roles` / `permissions` / `user_roles` / `role_permissions`，`resource:action` 命名（`app/lib/rbac/permissions.ts`） | 后台全部业务页面的访问控制 |
| 角色继承 | `role_parents` 表 + `getRoleClosure`（多层继承、环检测） | 「运营」继承「只读客服」等分层授权 |
| 权限分组目录 | `permission_groups`（树形，icon/order） | 业务权限点按模块成组展示 |
| 组织/部门树 | `departments`（树形 parent_id） | 直接映射为「机构/工作室」 |
| DB 驱动导航菜单 | `menus` 表（`required_permission` 绑定权限点，`loadMenuTree` 按权限过滤） | 业务菜单随权限自动显隐 = 功能开关 |
| 站内通知 | `notifications` 表 + `app/routes/api/notifications.ts` | 订单/认证/提现事件通知 |
| 幂等注册模式 | `ensurePermission / ensurePermissionGroup / ensureBuiltinMenus`（`app/server.ts` 启动时执行） | 新业务权限点与菜单的注册范式 |
| 后台页面骨架 | `app/routes/admin/`（users/roles/permissions/menus/departments/sessions/profile/仪表盘） | 业务页面按同一模式新增 |
| 测试基建 | Vitest + `tests/`（rbac/menus/auth 等） | 业务模块沿用同一测试模式 |

**结论：IAM、后台框架、导航、会话、通知、组织树 = 已完成。陪玩业务只需新增领域表 + 领域服务 + 业务页面 + 权限点。**

## 三、核心抽象：从「陪玩」到「陪伴服务撮合」

这是整个方案「多行业通用」的**灵魂**。源系统的游戏领域术语，全部抽象为可配置实体：

| 源系统概念 | 通用抽象 | 配置载体 | 说明 |
| --- | --- | --- | --- |
| 游戏（王者/LOL/金铲铲…） | **服务类目** | 类目表 | 可配置，健身/陪诊/家教各建一套类目 |
| 段位等级（王者以下/王者以上乱杀…） | **资质等级** | 资质等级表 | 含认证方式、价格区间权益 |
| 按局 / 按小时计费 | **计费方式** | 计费规则枚举 | 按次/按小时/按时长，可扩展 |
| 技能认证（上传段位/考核） | **资质认证** | 认证流程 | 上传资质 + 考核 两种 |
| 护航单（达标标准+先行赔付） | **标准化套餐任务** | 套餐表 | 达标标准字段化，支持赔付 |
| 工会 | **机构/工作室** | 复用 `departments` 树 | 教练团队、陪诊公司、家教机构 |
| 爵位/称号 | **会员权益体系** | 会员/称号表 | 免广告/专属标识/折扣 |
| 金币 + 余额 | **双币账户** | 钱包表 | 站内币（消费）+ 可提现余额 |
| 服务标签（上分带飞/甜美音…） | **通用服务标签** | 标签表 | 按行业配置标签库 |
| 分销/邀请 | **推广返佣引擎** | 分销表 | 订单 + 抽成比例驱动 |

**核心结论**：行业差异全部沉淀在 **「类目 + 资质等级 + 计费规则 + 标签」四张配置表** 中；用户、服务、订单、支付、分账、认证、评价的业务骨架**完全不变**。

## 四、MVP 范围裁剪（P0 / P1 / P2）

源系统 19 模块、43 子页是「大而全」的成熟产品。MVP 只保留能跑通交易闭环的最小集：

### 4.1 P0（一期，必须）— 交易闭环 7 件套

| 模块 | 核心功能 | 落地方式（基于现有骨架） | 行业通用性 |
| --- | --- | --- | --- |
| 用户管理 | 注册/登录、用户分型、封禁 | **复用** `users`/`sessions` + admin/users 页面，扩展字段 | 通用 |
| 认证管理 | 实名 + 资质认证（上传/考核） | 新增 `certifications` 表 + 审核页 | 通用（换资质类型） |
| 类目管理 | 类目 + 资质等级 + 计费规则 | 新增 `categories` / `levels` 表 + 配置页 | **行业配置核心** |
| 服务管理 | 发布/上下架/标签/价格 | 新增 `services` 表 + 管理页 | 通用 |
| 订单管理 | 下单/接单/状态流转/取消退款 | 新增 `orders` 表 + 管理页 | 通用 |
| 支付 + 钱包 | 余额/金币双币、充值、支付 | 新增 `wallets` / `pay_flows` 表（MVP 期模拟支付） | 通用 |
| 分账结算 + 提现 | 平台/服务方分账、提现审核 | 新增 `settlements` 表 + 财务页 | 通用 |

> 以上 7 件套 + 现有后台基础（仪表盘、RBAC、菜单、通知）即可跑通「发布 → 下单 → 支付 → 交付 → 分账 → 提现」完整闭环。评价表 `reviews` 随订单一并交付。

### 4.2 P1（二期）— 增长与运营

| 模块 | 说明 | 触发场景 |
| --- | --- | --- |
| 分销/邀请返佣 | 订单抽成引擎 | 有拉新需求时 |

| 敏感词审核 | 内容合规 | 社区/评论/私信上线时 |
| 签到 | 留存激励 | 需要日活运营时 |
| 派单管理 | 平台/机构发布任务、抢单 | 机构侧有派单场景时 |
| 护航套餐 | 标准化任务 + 赔付 | 有「达标标准」类服务时 |

### 4.3 P2（三期/可选）— 增值变现

| 模块 | 说明 |
| --- | --- |
| 爵位/会员 | 订阅制收入 |
| 虚拟礼物 | 打赏变现（含语音房强绑定） |
| 工会/机构深化 | 多级抽成、预充值、冻结（在 `departments` 基础上加业务字段） |

## 五、通用化架构设计（基于现有骨架）

### 5.1 分层架构（现状即架构）

```
┌──────────────────────────────────────────────────────────┐
│ 路由层   app/routes/admin/*.tsx（HonoX SSR 页面）          │
│          app/routes/api/*.ts（JSON 接口）                  │
├──────────────────────────────────────────────────────────┤
│ 领域层   app/lib/<domain>/*.ts（业务服务，新增）           │
│          app/lib/rbac/*  app/lib/auth/*（已有，复用）      │
├──────────────────────────────────────────────────────────┤
│ 数据层   app/lib/db/schema.ts（drizzle 表定义，追加领域表）│
│          SQLite（better-sqlite3，WAL）                     │
├──────────────────────────────────────────────────────────┤
│ 横切     权限中间件（routes/admin/_middleware.ts）         │
│          ensure* 幂等注册（server.ts 启动时）              │
│          Vitest 测试（tests/）                             │
└──────────────────────────────────────────────────────────┘
```

### 5.2 四条关键设计原则

1. **行业零硬编码**：「类目 + 资质等级 + 计费规则 + 标签」四表配置驱动。新增行业 = 加类目 + 加等级 + 加标签，不动代码。
2. **模块可插拔 = 权限 + 菜单，不另造开关系统**：每个扩展模块注册一组权限点和一组菜单项（`menus.required_permission`）；要"关闭"某模块，只需把菜单 `status` 置 `hidden` 且不给角色授对应权限——沿用现有 `loadMenuTree` 的过滤机制即可。
3. **幂等注册沿用现有范式**：新业务权限点/分组/菜单全部写成 `ensure*` 函数，挂到 `app/server.ts` 启动序列；`admin` 角色由现有 `ensureBuiltinRolePermissions` 自动补全全量权限，无需手工维护。
4. **财务闭环收口**：钱包 + 支付流水 + 分账独立成 `app/lib/finance/` 领域模块，所有资金变动只走 `pay_flows` 一张流水表（双向记账），避免散落。

### 5.3 P0 权限点规划（`resource:action` 约定）

格式须通过现有 `validatePermissionName` 校验（小写字母/数字/下划线/连字符，至少一级 `:`）：

| 权限点 | 说明 | 菜单绑定 |
| --- | --- | --- |
| `service:read` / `service:manage` | 服务查看 / 上下架·推荐·删除 | 服务列表 |
| `category:manage` | 类目与标签配置 | 类目管理 |
| `level:manage` | 资质等级与价格区间配置 | 资质等级 |
| `order:read` / `order:manage` | 订单查看 / 取消·退款操作 | 订单管理 |
| `cert:review` | 实名/资质认证审核 | 认证管理 |
| `finance:withdraw:review` | 提现审核与打款标记 | 提现管理 |
| `finance:flow:read` | 财务流水查看与导出 | 财务流水 |

- **分组**：在 `permission_groups` 新增父组 `biz`（业务管理），上述权限按 resource 前缀自动归组（现有 `backfillPermissionGroups` 机制）。
- **角色**：`admin` 沿用现有自动补全；新增 `operator`（运营，授予 `biz` 组权限）；如需只读客服，可建 `viewer` 角色并让 `operator` 通过 `role_parents` 继承它，直接演示现有角色继承能力。
- **菜单 seed**：按现有 `MENU_SEED` 模式追加「业务管理」分组（类目/服务/订单/认证/财务各一项，`requiredPermission` 绑定上表权限点）。

### 5.4 分账模式（商业模式落点）

沿用源系统验证过的分账：平台抽取固定比例（比例进配置），剩余归服务方；站内币（金币）只能消费不能提现，可提现余额才可提现。**行业通用**：游戏抽成、健身抽成、陪诊抽成，只有「抽成比例」一个变量。

## 七、核心业务流程（MVP 3 条闭环）

### 闭环 1：服务下单（交易主线）

```
消费者浏览服务 → 下单(时长/次数 + 时间 + 备注) → 待支付
   ↓ 支付（余额/金币/充值后支付）
待接单 → 服务方接单 → 进行中 → 已完成 → 评价 → 自动分账入账
   ↓ 超时未接单
自动取消 → 退款 → 流水记入
```

### 闭环 2：分账结算（商业模式）

```
订单完成 → 按「平台:服务方」比例分账 → 服务方余额增加
   ↓ 服务方提现
提交提现申请 → 金额冻结 → 人工审核（finance:withdraw:review）→ 线下打款 → 标记已打款
（规则：最低门槛 + 固定档位 + 每日限次 + 1-3 工作日到账）
```

### 闭环 3：资质认证准入（供给侧门槛）

```
用户申请成为服务方 → 实名认证（身份证正反面）
   ↓ 通过（cert:review）
资质认证（上传资质 / 考核 二选一）→ 匹配资质等级
   ↓ 通过
获得该等级定价权益 → 可发布服务 → 进入接单池
```

> 三条闭环的关键节点（接单、审核、分账、打款）全部写 `notifications`，复用现有通知中心。

### 8.2 行业切换操作手册（新行业接入 ≤ 1 天）

1. **建类目**：在类目表新增行业分类树（如「陪诊」→「挂号/取药/检查陪同」）
2. **建资质等级**：配置等级 + 认证方式（上传/考核）+ 价格区间权益
3. **配标签库**：新增该行业的服务标签
4. **配计费方式**：选择按次/按小时/按时长（已有枚举直接选，无需开发）
5. **开/关功能模块**：后台调整菜单 `status` 与角色权限（如陪诊关语音房、家教关礼物），无需发版
6. **配置分账比例 + 提现档位**

> 全程后台配置完成，无需改代码、无需重新发版。

## 十、合规与风险提示

| 风险项 | 说明 | 规避 |
| --- | --- | --- |
| 支付合规 | 平台触碰资金有「二清」风险 | 走持牌聚合支付 + 分账通道，平台不沉淀客户资金 |
| 实名认证 | 服务方需实名，未成年人保护 | 接公安/运营商实名核验，禁未保接单 |
| 内容审核 | 评论/私信/社区敏感内容 | 接敏感词库 + 人工巡检 |
| 行业资质 | 陪诊不可代诊/代开药；健身需教练资质；家教需教师资质 | 资质认证设为强制准入 + 免责协议 |
| 税务 | 服务方收入需完税 | 平台代扣代缴或明确税务责任 |
| 灰产边界 | 陪玩/陪伴类易涉灰产 | 明确服务范围、实名、审核、举报通道 |
