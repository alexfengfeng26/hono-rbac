# 陪玩系统快速落地方案（多行业通用版）

> 版本：v1.0
> 日期：2026-08-15
> 依据：`游戏陪玩系统管理后台功能方案_v1.1.md`、`陪玩系统手机端功能与字段说明.md`、`功能清单.xls`
> 定位：把「游戏陪玩」抽象为通用的**「陪伴/陪练服务撮合平台」**，一套系统、多行业复用，MVP 核心闭环 2-4 周落地。

---

## 一、方案定位与目标

### 1.1 一句话定位

> 一套 **「服务提供者 — 平台 — 消费者」双边撮合系统**：服务方发布服务 → 认证准入 → 消费者下单支付 → 服务交付 → 平台/服务方分账结算。游戏陪玩只是它第一个落地场景。

### 1.2 核心目标

| 目标 | 量化指标 |
| --- | --- |
| 快速落地 | MVP 核心闭环 **2-4 周**上线 |
| 多行业复用 | 行业切换 = **改配置不改代码**，新行业接入 ≤ 1 天 |
| 低成本启动 | 单机/轻量云部署，1-2 人即可运营 |

### 1.3 适用行业（源生 + 可迁移）

| 行业 | 服务方 | 消费者 | 典型服务 |
| --- | --- | --- | --- |
| 游戏陪玩（源生） | 陪玩/代练 | 老板 | 上分带飞、娱乐陪玩、护航代练 |
| 健身陪练 | 健身教练 | 学员 | 私教课、减脂带练、动作纠正 |
| 才艺陪练 | 声乐/舞蹈老师 | 学员 | 练琴陪练、舞蹈陪练、K歌陪唱 |
| 陪诊 | 陪诊师 | 患者/家属 | 挂号陪诊、取药代跑、检查陪同 |
| 家教陪学 | 老师/学霸 | 家长/学生 | 作业辅导、考前冲刺、陪读 |
| 宠物陪玩 | 宠托/遛狗师 | 宠主 | 遛狗、上门喂养、宠物陪伴 |

## 二、核心抽象：从「陪玩」到「陪伴服务撮合」

这是整个方案「多行业通用」的**灵魂**。源系统的游戏领域术语，全部抽象为可配置实体：

| 源系统概念 | 通用抽象 | 配置载体 | 说明 |
| --- | --- | --- | --- |
| 游戏（王者/LOL/金铲铲…） | **服务类目** | 类目表 | 可配置，健身/陪诊/家教各建一套类目 |
| 段位等级（王者以下/王者以上乱杀…） | **资质等级** | 资质等级表 | 含认证方式、价格区间权益 |
| 按局 / 按小时计费 | **计费方式** | 计费规则枚举 | 按次/按小时/按时长，可扩展 |
| 技能认证（上传段位/考核） | **资质认证** | 认证流程 | 上传资质 + 考核 两种 |
| 护航单（达标标准+先行赔付） | **标准化套餐任务** | 套餐表 | 达标标准字段化，支持赔付 |
| 工会 | **机构/工作室** | 机构表 | 教练团队、陪诊公司、家教机构 |
| 爵位/称号 | **会员权益体系** | 会员/称号表 | 免广告/专属标识/折扣 |
| 金币 + 余额 | **双币账户** | 钱包表 | 站内币（消费）+ 可提现余额 |
| 服务标签（上分带飞/甜美音…） | **通用服务标签** | 标签表 | 按行业配置标签库 |
| 分销/邀请 | **推广返佣引擎** | 分销表 | 订单 + 抽成比例驱动 |

**核心结论**：行业差异全部沉淀在 **「类目 + 资质等级 + 计费规则 + 标签」四张配置表** 中；用户、服务、订单、支付、分账、认证、评价的业务骨架**完全不变**。

## 三、MVP 范围裁剪（P0 / P1 / P2）

源系统 19 模块、43 子页是「大而全」的成熟产品。MVP 只保留能跑通交易闭环的最小集：

### 3.1 P0（一期，必须）— 交易闭环 7 件套

| 模块 | 核心功能 | 裁剪理由 | 行业通用性 |
| --- | --- | --- | --- |
| 用户管理 | 注册/登录、用户分型、封禁 | 一切业务的主体 | 通用 |
| 认证管理 | 实名 + 资质认证（上传/考核） | 服务方准入门槛，决定定价权益 | 通用（换资质类型） |
| 类目管理 | 类目 + 资质等级 + 计费规则 | 行业差异的唯一落点 | **行业配置核心** |
| 服务管理 | 发布/上下架/标签/价格 | 供给侧商品 | 通用 |
| 订单管理 | 下单/接单/状态流转/取消退款 | 交易主线 | 通用 |
| 支付 + 钱包 | 余额/金币双币、充值、支付 | 资金流入口 | 通用 |
| 分账结算 + 提现 | 平台/服务方分账、提现审核 | 商业模式落点 | 通用 |

> 以上 7 件套 + 后台基础（仪表盘、系统设置、子账号/角色权限）即可跑通「发布 → 下单 → 支付 → 交付 → 分账 → 提现」完整闭环。

### 3.2 P1（二期）— 增长与运营

| 模块 | 说明 | 触发场景 |
| --- | --- | --- |
| 分销/邀请返佣 | 订单抽成引擎 | 有拉新需求时 |
| 社区动态 | 内容留存 | C 端有内容属性时 |
| 敏感词审核 | 内容合规 | 社区/评论/私信上线时 |
| 签到 | 留存激励 | 需要日活运营时 |
| 派单管理 | 平台/机构发布任务、抢单 | 机构侧有派单场景时 |
| 护航套餐 | 标准化任务 + 赔付 | 有「达标标准」类服务时 |

### 3.3 P2（三期/可选）— 增值变现

| 模块 | 说明 |
| --- | --- |
| 爵位/会员 | 订阅制收入 |
| 虚拟礼物 | 打赏变现（含语音房强绑定） |
| 工会/机构 | 多级组织与抽成 |
| 试音/音乐厅 | 语音互动房间（技术重、依赖实时音视频） |
| 页面装修 DIY | 首页组件化配置 |

**裁剪原则**：先跑通「钱」的闭环（P0），再做「流量/留存」（P1），最后做「增值/氛围」（P2）。每一期都先于行业需求验证，不提前建设。

## 四、通用化架构设计

### 4.1 分层架构

```
┌─────────────────────────────────────────────────────┐
│ 表现层    uniapp H5（用户端 + 服务端合一）  │  Web 管理后台（Vue3 + Element Plus）│
├─────────────────────────────────────────────────────┤
│ 应用层    订单中心 │ 支付中心 │ 分账引擎 │ 认证中心 │ 内容 │ 营销（可插拔开关）│
├─────────────────────────────────────────────────────┤
│ 领域层    ★ 配置驱动领域模型（不写死游戏/行业）                    │
│          类目表 + 资质等级表 + 计费规则表 + 标签表                 │
├─────────────────────────────────────────────────────┤
│ 数据层    MySQL（业务） + Redis（缓存/会话） + 对象存储（图片/资质）│
└─────────────────────────────────────────────────────┘
```

### 4.2 三条关键设计原则

1. **行业零硬编码**：源系统把「游戏、段位、按局/小时」写死在页面里，MVP 必须改成「类目 + 资质等级 + 计费规则 + 标签」四表配置驱动。新增行业 = 加类目 + 加等级 + 加标签，不动代码。
2. **模块可插拔**：对齐源系统「系统设置-功能开关」思路，试音/音乐/签到/分销/爵位/礼物/社区等做成开关，按行业按需开启（陪诊不需要语音房，家教不需要礼物打赏）。
3. **财务中台抽离**：双币账户（站内币 + 可提现余额）+ 平台流水 + 分账引擎独立成模块，源系统「金币贯穿礼物/签到/分销/爵位」的记账逻辑全部收口到财务中台，避免散落。

### 4.3 分账模式（商业模式落点）

沿用源系统验证过的分账：平台抽取固定比例，剩余归服务方；站内币（金币）只能消费不能提现，可提现余额才可提现。**行业通用**：游戏抽成、健身抽成、陪诊抽成，只有「抽成比例」一个变量。

## 六、核心业务流程（MVP 3 条闭环）

### 闭环 1：服务下单（交易主线）

```
消费者浏览服务 → 下单(时长/次数 + 时间 + 备注) → 待支付
   ↓ 支付（余额/金币/充值后支付）
待接单 → 服务方接单 → 进行中 → 已完成 → 评价 → 自动分账入账
   ↓ 超时未接单
自动取消 → 退款 → 流水记入
```

### 闭环 2：分账结算（商业模式）

```
订单完成 → 按「平台:服务方」比例分账 → 服务方余额增加
   ↓ 服务方提现
提交提现申请 → 金额冻结 → 人工审核 → 线下打款 → 标记已打款
（规则：最低门槛 + 固定档位 + 每日限次 + 1-3 工作日到账）
```

### 闭环 3：资质认证准入（供给侧门槛）

```
用户申请成为服务方 → 实名认证（身份证正反面）
   ↓ 通过
资质认证（上传资质 / 考核 二选一）→ 匹配资质等级
   ↓ 通过
获得该等级定价权益 → 可发布服务 → 进入接单池
```

### 7.2 行业切换操作手册（新行业接入 ≤ 1 天）

1. **建类目**：在类目表新增行业分类树（如「陪诊」→「挂号/取药/检查陪同」）
2. **建资质等级**：配置等级 + 认证方式（上传/考核）+ 价格区间权益
3. **配标签库**：新增该行业的服务标签
4. **配计费方式**：选择按次/按小时/按时长（已有枚举直接选，无需开发）
5. **开/关功能模块**：在系统设置里关闭该行业不需要的模块（如陪诊关语音房、家教关礼物）
6. **配置分账比例 + 提现档位**

> 全程后台配置完成，无需改代码、无需重新发版。

## 八、技术选型与落地里程碑

### 8.1 技术栈建议

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 移动端 | uniapp（H5 双端合一） | 一套代码同时出用户端 + 服务端，成本低 |
| 管理后台 | Vue3 + Element Plus | 生态成熟、表格表单组件齐全 |
| 后端 | Node.js(NestJS) 或 Java(Spring Boot) | 团队熟悉度优先 |
| 数据库 | MySQL + Redis | 事务（订单/分账）+ 缓存 |
| 支付 | 微信/支付宝聚合支付 + 分账通道 | 规避二清，走持牌机构 |
| 存储 | 对象存储（COS/OSS） | 图片/资质材料 |

### 8.2 四周里程碑

| 周 | 交付内容 | 验收标准 |
| --- | --- | --- |
| Week 1 | 数据模型 + 认证 + 服务 + 订单 | 服务方可发布、消费者可下单 |
| Week 2 | 支付 + 分账 + 管理后台 | 全流程可支付、可分账、后台可运营 |
| Week 3 | 移动端双端 + 联调 | 手机端跑通下单→接单→完成→提现 |
| Week 4 | 上线 + 多行业配置验证 | 用第二个行业验证「改配置不改代码」 |

## 九、合规与风险提示

| 风险项 | 说明 | 规避 |
| --- | --- | --- |
| 支付合规 | 平台触碰资金有「二清」风险 | 走持牌聚合支付 + 分账通道，平台不沉淀客户资金 |
| 实名认证 | 服务方需实名，未成年人保护 | 接公安/运营商实名核验，禁未保接单 |
| 内容审核 | 评论/私信/社区敏感内容 | 接敏感词库 + 人工巡检 |
| 行业资质 | 陪诊不可代诊/代开药；健身需教练资质；家教需教师资质 | 资质认证设为强制准入 + 免责协议 |
| 税务 | 服务方收入需完税 | 平台代扣代缴或明确税务责任 |
| 灰产边界 | 陪玩/陪伴类易涉灰产 | 明确服务范围、实名、审核、举报通道 |
